# how-to
Okay, you want me to "teach you the software and try to make it more efficient." That's a good approach. Understanding the why behind each component will help you spot inefficiencies or areas for improvement. This is about deep comprehension, not just surface-level bug fixing.

Let's do it. We'll walk through the Gravitus Principia Core Engine, module by module, as defined by your directory structure. For each module, I'll explain its role, how it works, and then we can discuss potential areas for optimization or refinement.

We'll start at the bottom of the compilation pipeline and work our way up: Lexical Analysis (tokens/).

Module 1: tokens/ (Lexical Analysis)
Role: This is the first stage of your Gravitus Principia engine. Its job is to read the raw .grav source code file, character by character, and convert it into a stream of meaningful "tokens." Think of tokens as the individual words and symbols of your language.

Analogy: Imagine a factory assembly line. The tokens/ module is like the first station where raw, undifferentiated material (the .grav file's text) is cut and sorted into basic, identifiable parts (tokens) like "numbers," "identifiers," "operators," "delimiters," etc. It doesn't understand the meaning of these parts yet, just what they are.

Key Files & Their Purpose:

char_stream.hpp / char_stream.cpp:

Purpose: This component is responsible for robust file I/O. It reads characters from your .grav source file. It often provides features like peeking at the next character without consuming it, managing line and column numbers for error reporting, and handling the end of the file.
How it contributes to efficiency: An efficient char_stream minimizes disk I/O operations and provides fast character access, which is fundamental since every character in your source file will pass through here.
Efficiency Considerations:
Buffering: Is it reading character by character, or is it buffering chunks of the file into memory? Buffering significantly improves performance for large files.
Error Reporting: Does it accurately track line/column numbers? This is crucial for later debugging.
token.hpp / token.cpp:

Purpose: This file defines the Token class or struct. A Token object encapsulates information about a recognized lexical unit. Typically, it stores:
Type: An enum value (e.g., TokenType::IDENTIFIER, TokenType::NUMBER, TokenType::KEYWORD_IF, TokenType::OPEN_PAREN). Your AstNodeType enum might also play a role here, but TokenType is typically distinct for lexical units.
Lexeme (Value): The actual string of characters that formed the token (e.g., "my_variable", "123.45", "def").
Location: Line and column numbers where the token was found in the source file.
How it contributes to efficiency: A well-designed Token object is lightweight and easy to create and store. Efficient comparison and hashing of tokens can speed up later parsing stages.
Efficiency Considerations:
std::string vs. string_view: If the lexeme is stored as a std::string, it incurs memory allocation for each token. For performance, especially with large files, consider std::string_view (C++17+) which provides a non-owning view into the underlying char_stream buffer, avoiding copies and allocations. The char_stream would then need to ensure its buffer lives long enough.
Token Type Enum: Make sure the enum is comprehensive and covers all your Gravitus Principia syntax elements precisely.
lexer.cpp / lexer.hpp (public_lexer.cpp could be an implementation detail of lexer.cpp or a separate interface for different lexing modes):

Purpose: This is the heart of the lexer. It contains the state machine logic that reads characters from the char_stream, identifies patterns, and produces Token objects. It implements the rules for recognizing identifiers, keywords, numbers (including /n, /p, /a suffixes), strings, comments (#, ##), operators (*, +, =, :), delimiters ((, ), {, }, [, ], ,, ;, _, |), and your unique path navigations (/, //, ///).
How it contributes to efficiency: An efficient lexer is fast. It minimizes backtracking, uses optimized character-matching techniques, and avoids unnecessary allocations.
Efficiency Considerations:
Optimized Character Classification: Use std::isspace, std::isdigit, std::isalpha, etc., or pre-computed lookup tables for character classification for speed.
Keyword Hashing/Lookup: For keywords (like if, else, let, func), store them in an efficient std::unordered_map<std::string, TokenType> for fast lookup when an identifier is recognized.
Error Handling: The lexer should report lexical errors (e.g., unclosed multi-line comments, invalid characters) without crashing, providing clear line/column numbers.
State Machine Design: A well-designed state machine will avoid redundant checks and transitions.
How it all connects: The main.cpp (or a Compiler class) will typically instantiate a CharStream and a Lexer. The Lexer then uses the CharStream to read input and produces a stream (e.g., a std::vector<Token>) of Token objects, which are then passed to the parser/ module.

# AstNode Base Class:
It correctly defines the common interface for all AST nodes: type_, line_, column_. This is invaluable for consistent error reporting and debugging.
The virtual ~AstNode() = default; ensures proper polymorphic destruction using std::unique_ptr, preventing memory leaks when deleting derived node types through a base class pointer.
The virtual void accept(visitors::AstVisitor& visitor) = 0; is the cornerstone of your Visitor Pattern implementation. By making it a pure virtual function, you enforce that every single concrete AST node must implement this method, guaranteeing that your AST is ready for any visitor operation you throw at it (type checking, visualization, etc.).
Modular Includes: At the very end, you're including "h/declarations.hpp", "h/expressions.hpp", and "h/statements.hpp". This is smart. It means ast_node.hpp acts as a single, convenient include for any part of your compiler (especially the parser/ module) that needs to see the full definitions of all AST nodes. You avoid having to include dozens of individual node headers everywhere.
This is a well-engineered header. It lays a solid, extensible, and memory-safe foundation for your entire parsing and interpretation pipeline.
